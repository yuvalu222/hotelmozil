# Android non-companion routing options (system proxy/PAC, Enterprise, in-app VpnService) and Google Play / affiliate policy risk for HotelMozil

Scope: routing only Agoda (com.agoda.mobile.consumer) and Booking (com.booking) official Android app traffic via developer relay -> DataImpulse residential proxy in another country. Research date 2026-09-24. Tool budget limited; several items marked as inference or gap.

## 1. Android Wi-Fi manual proxy / PAC (and global adb proxy)

### Takeaway
Android supports a per-Wi-Fi-network manual proxy or PAC URL (PAC API since API 21), but it is only a "recommendation" that apps may ignore, applies to the Wi-Fi network it is configured on (not mobile data), has no username/password field, and cannot be set programmatically by a normal app (only device/profile owner). It is the lowest-friction "no install" route for users on Wi-Fi, but unreliable and brittle, and cannot carry DataImpulse credentials, so the relay must be IP-allowlisted or open (dangerous) - effectively unusable for a consumer on mobile data.

### Cited Findings
- `ProxyInfo` docs: "Proxy configurations are already integrated within the java.net and Apache HTTP stack. So URLConnection and Apache's HttpClient will use them automatically. Other HTTP stacks will need to obtain the proxy info by watching for the Proxy.PROXY_CHANGE_ACTION broadcast and calling methods such as ConnectivityManager.getDefaultProxy()." — [Android ProxyInfo](https://developer.android.com/reference/android/net/ProxyInfo)
- `ProxyInfo.buildPacProxy(Uri)` added in API level 21 ("download and run the PAC script at the specified URL"); `buildPacProxy(Uri, int port)` added API 30. — [Android ProxyInfo](https://developer.android.com/reference/android/net/ProxyInfo)
- The Wi-Fi settings UI option "Proxy Auto-Config" (PAC URL) is described as added in Android 6 Marshmallow (secondary source; API existed since 5.0). — [ctrl.blog via search summary](https://www.ctrl.blog/entry/android-proxyhandler-battery-optimization/)
- PAC implementation relies on two system helper apps: ProxyHandler (routes connections via the chosen proxy) and PacProcessor (evaluates the PAC). Since Android 7 battery optimization could stop them running in background, so requests queue until the app times out; reported for Android 7-9 and Google called it "working as intended"; workaround is to exempt ProxyHandler/PacProcessor from battery optimization. — [ctrl.blog](https://www.ctrl.blog/entry/android-proxyhandler-battery-optimization/)
- AOSP `PacProxySelector` binds to the system service `com.android.net.IProxyService`, parses PAC results `DIRECT`, `PROXY host:port`, and `SOCKS host:port` (SOCKS is parsed), and strips path and username/password from the URL before giving it to the PAC script ("so it's not visible to PAC script"). — [AOSP PacProxySelector.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/net/PacProxySelector.java); related [PacProxyManager.java](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/net/PacProxyManager.java)
- Proxy is configured per Wi-Fi network (saved in that SSID's configuration); the cellular equivalent is the APN proxy field, which many carriers ignore or lock; manual proxy settings only apply to Wi-Fi and mobile data bypasses them. — [ProxyWing 2026 guide](https://proxywing.com/blog/how-to-set-up-a-proxy-on-android-devices); [VoidMob](https://voidmob.com/blog/how-to-use-proxy-on-mobile-tutorial); [proxy-cheap 2026 guide](https://www.proxy-cheap.com/blog/how-to-set-up-android-proxy-settings)
- Built-in Wi-Fi proxy settings have no username/password fields; an authenticating proxy returns HTTP 407. — [Byteful](https://byteful.com/blog/setup-android-proxy); [DEV Community 2026 guide](https://dev.to/mathewtech/how-to-set-up-a-proxy-on-android-complete-guide-for-2026-4jk6)
- Apps with their own networking stack, QUIC, or DoH may bypass system proxy; "Many apps (banking, games, streaming) ignore Android's proxy API." (commercial blogs, not primary). — [ProxyVero](https://www.proxyvero.com/guide/how-to-set-up-a-proxy-on-android/); [aimultiple](https://aimultiple.com/android-proxy-server-settings)
- OkHttp: if `proxySelector` is unset, "the system-wide default proxy selector will be used" (so OkHttp usually honors the Android system/Wi-Fi proxy). — [OkHttp proxySelector docs](https://square.github.io/okhttp/5.x/okhttp/okhttp3/-ok-http-client/-builder/proxy-selector.html)
- OkHttp known bug: after a proxy route fails once, subsequent requests may bypass the Android system proxy; proxy values can be ignored after toggling Wi-Fi. — [okhttp #1203](https://github.com/square/okhttp/issues/1203); [okhttp #2525](https://github.com/square/okhttp/issues/2525)
- Cronet "will respect system wide proxy settings but does not currently provide an API to change proxies" per-request (Chromium mailing list). — [chromium net-dev: Adding proxy support to Cronet](https://groups.google.com/a/chromium.org/g/net-dev/c/FWnRnbJjvnM); [Cronet proxy support thread](https://groups.google.com/a/chromium.org/g/chromium-dev/c/AlBilpCBUBM)
- Microsoft documents that Edge on Android 13 ignores PAC configured in per-app VPN profiles (example of Chromium-based apps and PAC edge cases). — [Microsoft Learn](https://learn.microsoft.com/en-us/troubleshoot/mem/intune/device-enrollment/edge-ignore-pac-android-vpn-profile)
- Evidence specific to Booking app: SerpApi's guide on capturing Android HTTPS traffic (emulator, Charles as system proxy) says "open an app, say Booking.com, and you should see https traffic showing on the list" - i.e. the Booking app's traffic did go through the system proxy in that setup (with a patched/trusted CA). — [SerpApi blog](https://serpapi.com/blog/capturing-https-traffic-on-android-devices/)
- `WifiConfiguration.setHttpProxy(ProxyInfo)`: "This method should only be used by a device owner or profile owner. When other apps attempt to save a WifiConfiguration with modified proxy settings, the methods WifiManager.addNetwork and WifiManager.updateNetwork fail and return -1." (WifiConfiguration itself is deprecated in favor of WifiNetworkSuggestion.) — [WifiConfiguration](https://developer.android.com/reference/android/net/wifi/WifiConfiguration)
- `WifiNetworkSuggestion.Builder` has no proxy setter (checked the reference page; no proxy method present). — [WifiNetworkSuggestion.Builder](https://developer.android.com/reference/android/net/wifi/WifiNetworkSuggestion.Builder)
- Deep link: `Settings.ACTION_WIFI_SETTINGS` ("android.settings.WIFI_SETTINGS") shows Wi-Fi settings; "In some cases, a matching Activity may not exist, so ensure you safeguard against this." There is no documented intent to open a specific network's proxy editor. — [Settings](https://developer.android.com/reference/android/provider/Settings)

### Inferences
- Global adb proxy (`adb shell settings put global http_proxy host:port`, cleared with `:0`) is a developer/debug mechanism requiring USB debugging and a computer; not viable for consumers. (Well-known, but I did not fetch a primary source this session.)
- A PAC URL on Wi-Fi could route only *.agoda.* / *.booking.* / *.bstatic.com to the relay and DIRECT for everything else - functionally close to the iOS per-domain intent - but: (a) only on the configured Wi-Fi SSID(s), user must re-enter for each network; (b) no auth, so relay must authenticate by source IP or be an open proxy (abuse risk; open proxy to DataImpulse would be a resale/abuse liability); (c) the relay would need to speak plain HTTP CONNECT (or SOCKS) - DataImpulse creds would be added by the relay upstream.
- For PAC, Android typically exposes the system proxy to apps as a local ProxyHandler (localhost:port) that evaluates the PAC; apps that read `ConnectivityManager.getDefaultProxy()` or the java.net ProxySelector get it. Moderate confidence (derived from AOSP component names above; not verified line-by-line).
- QUIC: Chromium's network stack generally does not use QUIC through an HTTP proxy, so a Cronet-based app that honors the system proxy should fall back to TCP/TLS via CONNECT; an app with its own QUIC stack could bypass. Unverified for Agoda/Booking.
- Agoda app: no public evidence found either way. Booking app: weak evidence it honors system proxy (SerpApi emulator test).

### Gaps
- No primary evidence of which HTTP stack Agoda/Booking Android apps currently use (OkHttp vs Cronet) or whether they pin certificates (pinning does not matter for a pass-through CONNECT proxy, only for MITM).
- Did not verify whether PAC on Android is honored by apps that use OkHttp with default ProxySelector in current Android versions (14-16), nor the current state of the ProxyHandler background-restriction bug beyond Android 9.
- Primary source for adb `settings put global http_proxy` not fetched.

## 2. Android Enterprise / DPC and any Android "Relay" equivalent

### Takeaway
All programmatic proxy/VPN-forcing APIs (setRecommendedGlobalProxy, setAlwaysOnVpnPackage, WifiConfiguration proxy) require device owner or profile owner. Device owner requires factory-reset provisioning - infeasible for consumers; a work profile is possible but Agoda/Booking would have to be installed inside it. Android has no OS-level equivalent to Apple's Relay (MASQUE / Oblivious HTTP) payload as of this research.

### Cited Findings
- `DevicePolicyManager.setRecommendedGlobalProxy`: "Set a network-independent global HTTP proxy... This method requires the caller to be the device owner. This proxy is only a recommendation and it is possible that some apps will ignore it." Can't be set if there are unaffiliated secondary users/profiles. Throws SecurityException if not device owner. — [DevicePolicyManager](https://developer.android.com/reference/android/app/admin/DevicePolicyManager)
- `setAlwaysOnVpnPackage`: "Called by a device or profile owner to configure an always-on VPN connection through a specific application for the current user"; VPN app must declare VpnService guarded by BIND_VPN_SERVICE and target API 24+. Lockdown "carries the risk that any failure of the VPN provider could break networking for all apps." — [DevicePolicyManager](https://developer.android.com/reference/android/app/admin/DevicePolicyManager)
- Apple Relay: "a special type of proxy... two standard protocols defined by the IETF: MASQUE and Oblivious HTTP"; MASQUE relays use TLS 1.3 and QUIC/HTTP3. — [Apple WWDC23 "Ready, set, relay"](https://developer.apple.com/wwdc23/10002); [Apple Platform Deployment](https://support.apple.com/guide/deployment/dep91a6e427d)
- Secondary sources state Android has no built-in equivalent to Apple's MASQUE relay and relies on third-party VpnService apps for per-app routing. — [search summary of ProxyWing / proxy-cheap 2026 guides](https://proxywing.com/blog/how-to-set-up-a-proxy-on-android-devices)
- `VpnService.Builder.setHttpProxy`: "This proxy is only a recommendation... PAC proxies are not supported over VPNs." Split tunnel + proxy "generally won't work as expected". — [VpnService.Builder](https://developer.android.com/reference/android/net/VpnService.Builder)

### Inferences
- A profile-owner (work profile) DPC could set always-on VPN for the work profile, but the user would need to install Agoda/Booking inside the work profile and HotelMozil would need to act as a DPC - heavy UX, and Play's policies for device-admin/DPC apps are strict. Not a consumer path.
- I found no Android 14/15/16 system feature allowing a consumer app or configuration file to install a per-app/per-domain relay (no "Relay" payload analog). Chrome's IP Protection is browser-only and Google-operated (not verified this session).

### Gaps
- Did not search Android 16 QPR / Android 17 release notes exhaustively for any new proxy/relay API; conclusion "no equivalent" rests on absence of evidence plus secondary sources.

## 3. Building VpnService into HotelMozil (addAllowedApplication) - Play policy

### Takeaway
Technically trivial (per-app allowlist of the two packages, tunnel to the relay). But Play's VpnService policy restricts VpnService to apps whose core functionality is VPN or a listed exception, and explicitly prohibits redirecting other apps' traffic "for monetization purposes (for example, redirecting ads traffic through a country different than that of the user)". A hotel-price affiliate app routing Agoda/Booking through a foreign residential IP to show different prices and earn commission is squarely at risk of being read as that. A separate "HotelMozil Connect" VPN app has a better core-functionality story but still faces the monetization/other-app-redirect clause and the proxy-services clause.

### Cited Findings
- Policy exceptions allowed to use VpnService for core functionality with remote servers: "Parental control and enterprise management apps, App usage tracking, Device security apps (for example, anti-virus, mobile device management, firewall), Network-related tools (for example, remote access), Web browsing apps, Carrier apps..." — [Understanding Google Play's VpnService policy](https://support.google.com/googleplay/android-developer/answer/12564964)
- Prohibited: "Collect personal and sensitive user data without prominent disclosure and consent" and "Redirect or manipulate user traffic from other apps on a device for monetization purposes (for example, redirecting ads traffic through a country different than that of the user)." — [Play VpnService policy](https://support.google.com/googleplay/android-developer/answer/12564964)
- "All apps that use the VpnService must complete the declaration form" (deadline was Aug 31, 2023). Apps "must encrypt the data from the device to the VPN tunnel endpoint." — [Play VpnService policy](https://support.google.com/googleplay/android-developer/answer/12564964)
- Only apps that have VPN as core functionality (or an exception) may create a device-level tunnel to a remote server; apps outside permitted functionality are rejected and told to remove VPN services from all release tracks. — [Permissions and APIs that Access Sensitive Information](https://support.google.com/googleplay/android-developer/answer/16558241); [Policy announcement July 27, 2022](https://support.google.com/googleplay/android-developer/answer/14554661)
- Precedent: developer thread "App rejected for VpnService although it is the core functionality" (content not retrievable); a dVPN app reported repeated Play rejections. — [Play Developer Community thread](https://support.google.com/googleplay/android-developer/thread/235925715/app-rejected-for-vpnservice-although-it-is-the-core-functionality?hl=en); [Qubetics blog](https://www.qubetics.com/blog/android-dvpn-build-status-why-google-play-keeps-rejecting-it/)
- Device and Network Abuse: "Apps that facilitate proxy services to third parties may only do so in apps where that is the primary, user-facing core purpose of the app." — [Device and Network Abuse policy](https://support.google.com/googleplay/android-developer/answer/16559646)
- `addAllowedApplication`: "If this method is called at least once, only applications added through this method (and no others) are allowed access... other, un-added applications will use networking as if the VPN wasn't running." Package must be installed (NameNotFoundException otherwise). — [VpnService.Builder](https://developer.android.com/reference/android/net/VpnService.Builder)
- VpnService: user consent required first time (`prepare()`), only one VPN at a time (starting one deactivates another), system notification shown while active. — [VpnService](https://developer.android.com/reference/android/net/VpnService)
- VPN "Independent security review" badge: based on App Defense Alliance MASA (MASVS); voluntary; ~2-3 weeks; launched Nov 2023 starting with VPN apps. — [The Hacker News](https://thehackernews.com/2023/11/google-play-store-introduces.html); [BleepingComputer](https://www.bleepingcomputer.com/news/security/google-play-adds-security-audit-badges-for-android-vpn-apps/); [Help Net Security](https://www.helpnetsecurity.com/2023/11/06/google-vpn-apps-security/)

### Inferences
- Embedding VpnService into the main hotel-price app: high rejection risk - core purpose (price comparison/affiliate) is not VPN and not on the exceptions list; also the "monetization ... through a country different than that of the user" example is close to HotelMozil's model (commission on bookings whose price was obtained via a foreign IP).
- Separate "HotelMozil Connect" VPN app: can truthfully declare VPN as core functionality, must encrypt (WireGuard/TLS to relay ok; relay->DataImpulse leg is beyond the device-to-endpoint requirement), must disclose data handling. Remaining risks: reviewer linking it to affiliate monetization of other apps' traffic; "proxy services to third parties" clause (routing through a residential proxy network) is permitted only when it is the primary user-facing purpose, which a dedicated app could satisfy. Moderate risk, not low.
- MASA badge is optional and doesn't grant policy approval; useful only as trust signal.
- Mitigation ideas (inference): present it as a user-initiated "compare prices from another region" privacy/VPN tool, no ad injection, no traffic modification, user chooses country, clear disclosure; avoid tying tunnel usage to commission in listing/declaration.

### Gaps
- Exact Play Console VpnService declaration questions not retrieved (form content behind console login).
- No public enforcement case found specifically for travel/price-comparison apps using VpnService.

## 4. Companion-app approach (deep link to WireGuard/Outline) policy risk + Agoda/Booking affiliate terms

### Takeaway
Play has no general ban on linking users to other legitimate Play apps; the relevant clauses target facilitating malware, hacking/circumventing security, and interfering with other apps' ads. Since HotelMozil itself would not use VpnService, the VpnService policy doesn't apply to it; the proxy-services clause is the main Play-side ambiguity. The bigger risk is contractual: Agoda's affiliate agreement forbids obtaining commissions by "any other scheme or trick" and anything that "cause[s] detriment to Agoda", and prohibits using Agoda Data for Price Comparison purposes - a geo-arbitrage proxy flow could be deemed a breach with commission forfeiture.

### Cited Findings
- Device and Network Abuse prohibits: "Apps that block or interfere with another app displaying ads"; "Apps that facilitate or provide instructions on how to hack services, software or hardware, or circumvent security protections"; "Apps that link to or facilitate the distribution or installation of malicious software"; and proxy services to third parties only when primary core purpose. — [Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16559646)
- Agoda Online Affiliate Agreement (v.2023) cl. 4.1.5: Affiliate shall not "(a) programmatically evaluate or otherwise extract information ... from any part of the Agoda Website ... scrape..."; "(d) (attempt to) obtain credit or Commissions from Agoda by misrepresentation, false statements, fraudulent behavior or any other scheme or trick; or (e) otherwise (attempt to) cause detriment to Agoda or the Agoda Website. Any violation ... will be deemed a material breach ... resulting in ... forfeiture of any Commissions." — [Agoda Online Affiliate Agreement PDF](https://partners.agoda.com/Content/pdf/Agoda_OnlineAffiliateAgreement.pdf)
- Agoda cl. 3.2.2: Affiliate may not use/disclose Agoda Data "(ii) for Price Comparison purposes, sites, reviews or investigations"; "Price Comparison" defined as comparison of accommodation prices/availability from two or more booking platforms. Cl. 4.1.2: not interfere with Agoda's relationship with Accommodations. "Agoda Websites" includes Agoda mobile applications. — [Agoda Online Affiliate Agreement PDF](https://partners.agoda.com/Content/pdf/Agoda_OnlineAffiliateAgreement.pdf)
- Agoda Partner Center Terms of Use prohibit "speculative, false, or fraudulent bookings", automated access/scraping, and to "bypass or circumvent other measures employed to prevent or limit access". — [Agoda Affiliate Terms of Use PDF](https://partners.agoda.com/Content/pdf/Agoda_Affiliate_Terms_of_Use.pdf)
- Booking.com affiliate: latest agreement is in Partner Center footer; summaries report bans on redirecting Booking pages / iframes, replica sites, copying content (including from Agoda/Priceline/Kayak), 'Booking'-like domains, and (General Partner Terms v5) using an AI system without prior written approval. — [Booking affiliate KB (search result)](https://affiliates.support.booking.com/kb/s/article/Partner-Affiliate-Agreement); [General Partner Terms PDF](https://image.email.partnerships.booking.com/lib/fe3011737364047d711079/m/1/23929e0a-6a64-449c-90f4-1f9dac565e6e.pdf); [Vorp Labs on AI approval](https://vorplabs.com/agent-tools/booking-demand-api)

### Inferences
- Agoda: HotelMozil's core model (comparing Agoda vs Booking prices) may already conflict with 3.2.2 if it uses Agoda Data; adding foreign-IP routing to surface cheaper geo-prices plausibly falls under "scheme or trick" / "detriment to Agoda". Risk is commission forfeiture and termination rather than legal action. Note: the user booking inside the official Agoda app via a proxy may not even be attributed to the affiliate unless the deep link carries the affiliate CID; attribution with a foreign IP may also look anomalous to fraud systems.
- Play-side for companion flow: deep-linking to WireGuard/Outline (legit Play apps) and providing a config is not prohibited per se; keep listing/description transparent (Deceptive Behavior) and avoid framing as circumventing Agoda/Booking protections.
- Ranking of Play risk (inference): Wi-Fi PAC instructions (lowest) < companion app (WireGuard/Outline) < separate VPN app < VpnService inside main app (highest).

### Gaps
- Booking.com General Partner Terms PDF text could not be extracted (encoded font); no verified clause on proxies/VPN/geo pricing. No explicit "VPN/proxy" clause found in Agoda terms either - conclusions rely on general fraud/detriment clauses.
- Deceptive Behavior policy text not fetched this session.
